## ۱. هدف، Deliverable و خارج از اسکوپ

**هدف:** موتور تسویه چرخه‌ای فروشندگان + جدول کمیسیون + کیف پول دوبخشی فروشنده + موتور برداشت/واریز + گزارش‌های مالی ادمین. قواعد غیرقابل تغییر: **چرخه ۱ = ۳۰ روز از نخستین فروش تحویل‌شده (نه ثبت‌نام، نه تأیید فروشنده، نه پرداخت)**؛ **چرخه ۲ به بعد هر ۱۴ روز** (جدول نمونه: روز ۳۰ = اولین تسویه، روز ۴۴ دومین، روز ۵۸ سومین، روز ۷۲ چهارمین)؛ **برداشت زودهنگام چرخه ۱ ممنوع**، **چرخه ۲+ با کارمزد ۲٪ + تأیید دستی ادمین**؛ واریز = **۳ تلاش خودکار با فاصله ۱۵ دقیقه** وگرنه **صف دستی + تیکت خودکار**؛ کیف پول فروشنده **دو بخش: قابل برداشت / در انتظار تسویه + شمارش معکوس**؛ بازگشت وجه **بالای ۵ میلیون تومان = تأیید دوم**؛ **نقش مالی فقط خواندنی + تأیید تسویه**؛ همه مبالغ `NUMERIC(18,0)`؛ **هیچ retry خودکار مالی**؛ همه اقدامات مالی در `audit_logs` **فقط‌افزودنی**.

**Deliverable:**

| دسته | دقیقاً چه چیزی تحویل می‌شود |

**خارج از اسکوپ:** پرداخت/درگاه/`Idempotency-Key`/اسکروی اولیه/شارژ کیف پول/بازگشت ۰ تا ۱۰ ثانیه‌ای به کیف پول/فاکتور (**SP-07**)؛ لغو سفارش و جدول `cancellations` (**SP-06 — فقط ارجاع، بازسازی نمی‌شود**)؛ مرجوعی و `return_requests` (**SP-10**)؛ UI تیکت (**SP-14** — SP-09 فقط ردیف تیکت خودکار صف واریز را می‌سازد)؛ **ارسال واقعی اعلان تسویه (۲۴ ساعت قبل + نتیجه در روز تسویه) = فقط ثبت رویداد، اجرا پس از SP-11**؛ داشبورد کلان/نقش‌ها/لاگ سراسری (**SP-15**)؛ BNPL و اعتبار (غیرفعال طبق README بخش ۱/۸).

## ۳. اقدامات و مراحل (گام‌به‌گام با Milestone)

**M-09.1 — مدل داده، مهاجرت و سرویس کمیسیون (روز ۱-۲)**
1. نوشتن مهاجرت نسخه‌دار `settlements`، `commissions` و افزودن ستون‌های دوبخشی به `wallets` و ستون‌های `status/attempt/paid_at` به `wallet_transactions` + تمرین rollback در staging.
2. Seed تنظیمات مالی: درصد کمیسیون (تأیید 👤)، حداقل برداشت، سقف تأیید دوم = ۵,۰۰۰,۰۰۰ ریال/تومان طبق تنظیم ادمین (صفحه ۲۷).
3. پیاده‌سازی `CommissionService` با `effective_from`: محاسبه با نسخه‌ای که **در لحظه تحویل** معتبر بوده؛ «تغییر کارمزد یا چرخه فقط روی چرخه‌های آینده اعمال می‌شود».
4. اتصال به رویداد تحویل SP-08: آزادسازی اسکرو منهای کارمزد → ردیف `wallet_transactions` نوع `escrow_release` با برچسب `pending_settlement`.
   - **خروجی:** مهاجرت + seed + `CommissionService` + هندلر رویداد — **معیار قبولی:** `migration:run` و rollback پاس؛ تست `commission.effective-from` سبز؛ تغییر درصد، دوره بسته‌شده را دست نمی‌زند.

**M-09.2 — موتور تسویه و کیف پول دوبخشی (روز ۳-۴)**
1. سرویس تعیین مبدأ چرخه: **تاریخ نخستین سفارش با وضعیت «تحویل شده»** (نه ثبت‌نام/تأیید/پرداخت)؛ چرخه ۱ = ۳۰ روز، سپس هر ۱۴ روز؛ هیچ تسویه‌ای در وسط چرخه.
2. جابه‌جایی مبالغ از `pending_settlement` به `available` در «روز تسویه» + ساخت ردیف `settlements` (gross, commission, penalties, refunds, net).
3. شمارش معکوس و «اعلان تسویه ۲۴ ساعت قبل» = ثبت رویداد `REM-SETTLE` در صف (ارسال با SP-11).
4. منطق توقف: فروشنده مسدود/تعلیق → توقف چرخه و **ادامه از همان نقطه** پس از رفع.
   - **خروجی:** `SettlementEngine` + API سمت فروشنده — **معیار قبولی:** تست زمان مصنوعی: روز ۰ → روز ۳۰ → ۴۴ → ۵۸ → ۷۲ صحیح؛ سبد ۲ فروشگاهی = **۲ تسویه جدا** (پیوست ب سناریو ۴).

**M-09.3 — برداشت، واریز، تأیید دوم و کیف پول منفی (روز ۵-۶)**
1. `POST /wallet/withdrawals` برای مشتری (چرخه ۱۴ روزه، حداقل برداشت، کارمزد ۰ رایگان تا سقف ماهانه سپس مبلغ ثابت ادمین) و `POST /seller/wallet/early-withdrawals` برای فروشنده.
2. قواعد سخت: چرخه ۱ → بلاک برداشت زودهنگام؛ چرخه ۲+ → کارمزد **۲٪** + **تأیید دستی ادمین** (صف «درخواست برداشت زودهنگام»).
3. موتور واریز: **۳ تلاش خودکار با فاصله ۱۵ دقیقه** → شکست = وضعیت «صف دستی» + **تیکت خودکار** + دکمه «اجرای مجدد» دستی در پنل ۲۶ (**بدون retry خودکار دیگر**).
4. کیف پول منفی: `debt > 0` → **مسدودی برداشت تا تسویه** + **کسر از فروش بعدی** (`debt_deduction`)؛ بازگشت بالای ۵ میلیون → صف تأیید دوم (صفحه ۲۵)؛ هر اقدام مالی → `audit_logs` append-only با قبل/بعد.
   - **خروجی:** جریان کامل پول فروشنده/مشتری — **معیار قبولی:** سناریوهای C، D، E، F بخش ۴ دستی سبز؛ هیچ endpoint مالی‌ای بدون `Idempotency-Key`/لاگ audit نیست.

**M-09.4 — صفحات، گزارش‌ها، تست و Swagger (روز ۷-۸)**
1. پیاده‌سازی `wallet.png` در اپ، `seller-wallet.png` در پنل فروشنده، صفحات ۲۴/۲۵/۲۶/۲۷/۲۹ پنل ادمین (همه با حالت خالی/خطا از UI Copy).
2. سه گزارش ادمین: لیست تسویه‌ها، کمیسیون per دوره، **gross/net هر فروشنده در هر دوره** + خروجی اکسل/PDF.
3. نمای «فقط خواندنی» مالی (دکمه‌های اقدام غیرفعال + نشان قفل) و تأیید دوم نیازمند ادمین دوم با 2FA.
4. اجرای کل تست‌های بخش ۴ + به‌روزرسانی Swagger/`/docs` + ثبت رویدادهای آنالیتیکس.
   - **خروجی:** SP-09 قابل پذیرش — **معیار قبولی:** چک‌لیست DoD کامل سبز + پوشش Swagger ۱۰۰٪.

## ۴. روش تست و پذیرش (DoD)

**تست خودکار (نام‌ها):** `commission.effective-from.spec.ts` · `settlement.cycle-start-first-delivered.spec.ts` · `settlement.cycle14-schedule.spec.ts` · `settlement.multi-store-two-settlements.spec.ts` · `wallet.two-parts-countdown.spec.ts` · `withdrawal.cycle1-blocked.spec.ts` · `withdrawal.early-fee-2pct.spec.ts` · `payout.three-attempts-15min.spec.ts` · `payout.manual-queue-ticket.spec.ts` · `wallet.negative-balance-block.spec.ts` · `refund.second-approval-5m.spec.ts` · `rbac.finance-read-only.spec.ts` · `audit.append-only-financial.spec.ts` (پیوست ب ۸) · `contract.wallet-settlements.api.spec.ts`.

**سناریوی دستی گام‌به‌گام:**
- **الف — مبدأ چرخه:** فروشنده‌ای را روز ۱۰ تأیید کنید، اولین فروش تحویل‌شده‌اش روز ۴۵. در `seller-wallet.png` باید «در انتظار تسویه» + شمارش معکوس تا **روز ۷۵** ببینید و برداشت زودهنگام **مسدود** با پیام «برداشت زودهنگام در چرخه اول ممکن نیست. برداشت شما در روز تسویه انجام می‌شود.» (⚠️ متن طبق تصمیم بخش ۵).
- **ب — دو بخشی:** پس از تحویل، `GET /seller/wallet` → `available=0` و `pending_settlement=مبلغ خالص`؛ در `wallet.png` مشتری پیام حالت خالی «موجودی کیف پول شما صفر است».
- **ج — روز تسویه + شکست واریز:** اجرای job تسویه → ردیف `settlements` ساخته می‌شود → تأیید مالی → اجرا → ۳ بار شکست شبیه‌سازی (۱۵ دقیقه فاصله) → پس از تلاش سوم: وضعیت صف دستی + تیکت خودکار + ردیف `audit_logs` + اعلان رویداد `SMS-SETTLEMENT` در صف (`تسویه دوره {دوره} فروشگاه {نام}: {مبلغ} تومان به شبا {شبا_مخفف} واریز شد.`). هیچ تلاش چهارم خودکاری نباید رخ دهد.
- **د — برداشت زودهنگام چرخه ۲+:** مبلغ ۱,۰۰۰,۰۰۰ → کارمزد ۲٪ = ۲۰,۰۰۰ → واریز ۹۸۰,۰۰۰؛ بدون تأیید ادمین رد می‌شود؛ پس از رد: `SMS-WITHDRAW-NO` = «درخواست برداشت {مبلغ} تومان رد شد. دلیل: {دلیل}. مبلغ در کیف پول محفوظ است.»؛ پس از تأیید: «درخواست برداشت ثبت شد» + `SMS-WITHDRAW-OK`.
- **ه — تأیید دوم و مالی فقط‌خواندنی:** بازگشت ۸,۰۰۰,۰۰۰ تومانی → ورود با نقش «مالی» → اجرای بازگشت بلاک + پیام «سطح دسترسی ناکافی» + ایجاد درخواست «تأیید دوم»؛ ادمین دوم (2FA) تأیید می‌کند → اجرا ≤ ۱۰ ثانیه.
- **و — کیف پول منفی:** بدهی ۱۵۰,۰۰۰ → درخواست برداشت بلاک با پیام «برداشت شما تا تسویه بدهکاری مسدود است» (⚠️ تصمیم) → فروش بعدی ۵۰۰,۰۰۰ → کسر خودکار ۱۵۰,۰۰۰ → `available = ۳۵۰,۰۰۰`.
- **ز — حذف رکورد مالی (پیوست ب ۸):** تلاش DELETE → رد + `soft delete` + ردیف `audit_logs`.

- [ ] واریز دقیقاً ۳ تلاش ۱۵ دقیقه‌ای → صف دستی + تیکت خودکار؛ هیچ retry خودکار مالی دیگری وجود ندارد
- [ ] کیف پول منفی → مسدودی برداشت تا تسویه + کسر از فروش بعدی
- [ ] بازگشت > ۵ میلیون = تأیید دوم ادمین دوم با 2FA؛ نقش مالی فقط خواندنی + تأیید تسویه
- [ ] هر عملی مالی = یک ردیف `audit_logs` فقط‌افزودنی؛ حذف فیزیکی ممکن نیست
- [ ] همه ستون‌های پولی `NUMERIC(18,0)`؛ پاسخ `{success,data,meta}` / `{success:false,error{...}}`
- [ ] ۳ گزارش ادمین (تسویه، کمیسیون، gross/net هر فروشنده در هر دوره) + خروجی اکسل/PDF
- [ ] سبد ۲ فروشگاهی = ۲ سفارش مستقل + **۲ تسویه جدا** (پیوست ب ۴)
- [ ] Swagger ۱۰۰٪ endpointها؛ همه متن‌های کاربرپسند فارسی دقیقاً از UI Copy
