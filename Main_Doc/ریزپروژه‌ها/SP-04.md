## ۱. هدف، Deliverable و خارج از اسکوپ

**هدف:** پیاده‌سازی چرخه کامل «ثبت‌نام فروشنده»: انتخاب از میان **۱۰ نوع فروشنده** با فقط **۲ ترکیب مجاز**، بارگذاری مدارک اختصاصی هر نوع، عبور از **چک‌لیست ۵ موردی ادمین** و صدور یکی از ۴ تصمیم، سپس ارتقای فروشنده تأییدشده به **سطح «تازه‌کار» با ۷ روز مهلت ثبت اولین محصول**. در کنار آن «پنل فروشنده پایه» (داشبورد + پروفایل فروشگاه + آدرس ثبتی نسخه‌بندی‌شده) تحویل می‌شود.

**Deliverable:**

- **جداول (نام ثابت ERD):** `sellers` (`id, owner_id, name, type, status, rating, commission_id`)، `provider_applications` (`id, user_id, kind, docs(JSON), status, reviewed_by`)، `seller_addresses` (`id, seller_id, title, province, city, address_line, postal_code, tax_id, verified_by, verified_at, version`)، `audit_logs` (هر تصمیم ادمین)؛ جدول `providers` فقط ساختار می‌شود (پیاده‌سازی فاز ۲).
- **Endpointها (زیر `/api/v1`):**

| مسیر | نقش | توضیح |
|------|-----|-------|
| `POST /provider-applications` | فروشنده | ثبت‌نام + انتخاب نوع (۱۰ گزینه) + مدارک |
| `GET /provider-applications/{id}` | فروشنده | وضعیت + دلایل نقص + مهلت باقی‌مانده |
| `PATCH /provider-applications/{id}` | فروشنده | تکمیل نقص/ارسال مجدد |
| `POST /me/seller-addresses` · `PATCH /me/seller-addresses/{id}` | فروشنده | آدرس ثبتی (نسخه جدید، در انتظار تأیید) |
| `GET /providers/{id}` | عمومی | پروفایل عمومی فروشنده تأییدشده |
| `GET /admin/seller-applications?status=pending&page=` | ادمین | صف: قدیمی‌ترین اول + شمارش معکوس SLA |
| `POST /admin/seller-applications/{id}/decision` | ادمین | ۴ تصمیم: تأیید / رد / نقص اطلاعات / نیاز به بازبینی |
| `POST /admin/seller-applications/{id}/seller-address/{aid}/verify` | ادمین | تأیید/رد آدرس ثبتی (نسخه‌بندی) |
| `GET /admin/sellers` · `POST /admin/sellers/{id}/suspend` | ادمین | مدیریت + تعلیق با دلیل |

- **صفحات Flutter:** صفحه «فروشنده - در انتظار تأیید» با عنوان **«ثبت‌نام شما در انتظار تأیید ادمین است»** و دکمه «بازگشت به خانه»؛ انتخاب نقش «فروشنده» در «تکمیل پروفایل» (`wireframes/login.png`)؛ صفحه «نتیجه بررسی» (تأیید/رد/نقص با دلیل). فرم چندمرحله‌ای مدارک وایرفریم اختصاصی ندارد (`project-document.md` «صفحات بدون وایرفریم» ردیف ۱) و طبق دیزاین‌سیستم ساخته می‌شود.
- **صفحات وب پنل فروشنده (Next.js):** `wireframes/seller-dashboard.png` («داشبورد» با حالت خالی «هنوز فروشی نداشته‌اید» + راهنما)، «پروفایل فروشگاه» (نام/لوگو/نوع/ساعت کاری)، «آدرس ثبتی فروشگاه» (عنوان صفحه، دکمه «ارسال برای تأیید»، خطا: «پس از تأیید، تغییر نیازمند بررسی مجدد است»)، «صفحه نتیجه بررسی».
- **صفحات وب ادمین:** صفحه ۷ «صف تأیید فروشندگان»، صفحه ۸ «تعلیق و رفع تعلیق»، صفحه ۱۱ «تأیید آدرس ثبتی فروشگاه» — همگی داخل `wireframes/admin-panel.png`.
- **مهاجرت / seed / تست / Swagger:** ۳ مهاجرت + rollback در staging؛ seed داده آزمایشی ۳ فروشنده در ۳ وضعیت؛ تست‌های بخش ۴؛ پوشش Swagger ۱۰۰٪.

**خارج از اسکوپ:**
- ثبت محصول، لیستینگ، پیش‌بررسی ۱۰ شرطی و صف تأیید محصول → **SP-05** (که به هر دو SP-03 و SP-04 نیاز دارد).
- سفارش‌ها، ارسال/پیک، کیف پول و تسویه در پنل فروشنده → **SP-06 تا SP-09**.
- قالب‌های ۳۵ پیامک/۳۴ پوش/۹ ایمیل و کرون اعلان → **SP-11** (اینجا فقط اتصال به کانال mock).
- سرویس‌ها/خدمات، رزرو نوبت و `providers` عملیاتی → **فاز ۲** (جداول رزرو می‌شوند).
- نقش‌های RBAC کامل، 2FA و صفحات تعلیق سراسری ادمین → **SP-15**.

## ۳. اقدامات و مراحل (گام‌به‌گام با Milestone)

### M-04.1 — اسکیما و ماشین وضعیت (روز D1-D2)
1. ایجاد `Main_Code/apps/api/src/migrations/00X-sellers.sql`: `sellers`, `provider_applications`, `seller_addresses` با `UUIDv7`، `NUMERIC(18,0)`، soft-delete.
2. ستون `status` با مقادیر دقیق: **`PENDING`(در انتظار تأیید) / `APPROVED`(تأیید شده) / `NEEDS_INFO`(نقص اطلاعات) / `REJECTED`(رد شده) / `SUSPENDED`(معلق) / `INACTIVE`(غیرفعال)**.
3. `seller_addresses.version` + قید «حداقل ۱ و حداکثر ۳ آدرس فعال per فروشنده».
4. رمزنگاری AES-256 روی `tax_id` (شبا) و `audit_logs` بدون PII.
5. اجرای rollback در staging.

| خروجی مرحله | ۳ جدول + ماشین وضعیت ۶ حالته |
| معیار قبولی | rollback سبز؛ گذارهای غیرمجاز در تست واحد رد شوند |

### M-04.2 — ماتریس ۱۰ نوع، ۲ ترکیب و API ثبت‌نام (روز D3-D4)
1. پیاده‌سازی ماتریس نوع ← مدارک (اجباری/اختیاری) به‌صورت داده‌محور در `provider_applications.docs(JSON)`:

| نوع | مدارک/اطلاعات اختصاصی |
|-----|----------------------|
| پت‌شاپ | شماره ثبت، آدرس فروشگاه، نوع کالاها |
| گرومر | کد ملی، نمونه کار عکس، بیمه مسئولیت |
| کلینیک | پروانه فعالیت، شماره نظام پزشکی، لیست تجهیزات |
| بیمارستان | پروانه بیمارستانی، اورژانس، متخصصین |
| مطب دامپزشک | کد نظام دامپزشکی، محل مطب |
| متخصص دام بزرگ | منطقه فعالیت، ماشین‌آلات |
| پانسیون | مجوز فعالیت، ظرفیت نگهداری، عکس محل، ساعات کاری |
| بیمارستان + پانسیون | پروانه بیمارستانی + مجوز پانسیون، ظرفیت، امکانات |
| عمده‌فروش | شرکت ثبت شده، لیست اقلام عمده |
| واردکننده | کارت بازرگانی، مجوز واردات |

2. قاعده ترکیب: فقط **`بیمارستان+پانسیون`** و **`پت‌شاپ+کلینیک`** مجازند؛ هر ترکیب دیگر ← `VALIDATION_ERROR`.
3. اعتبارسنجی فیلدهای اجباری: نام فروشگاه، نوع فعالیت، شماره موبایل، شماره شبا («شماره شبا معتبر نیست»)، آدرس، لوگو/عکس (حداقل ۱)، شناسه ملی/شماره ثبت؛ «ساعت کاری» اختیاری.
4. دروازه مدرک: نوع «کلینیک/بیمارستان/مطب» بدون پروانه ← دکمه ارسال بلوکه + **«پروانه فعالیت الزامی است»**.
5. ثبت خودکار `status = PENDING` + افزودن آیتم به Action Queue ادمین + شمارش معکوس مهلت بررسی ۲۴ ساعته.

| خروجی مرحله | API ثبت‌نام + ماتریس مدارک + دروازه پروانه |
| معیار قبولی | سناریوی دستی ۱ تا ۴ بخش ۴ سبز شود |

### M-04.3 — صف ادمین: چک‌لیست ۵ موردی + ۴ تصمیم + مهلت ۷ روز (روز D5-D6)
1. صفحه صف (قدیمی‌ترین اول + شمارش معکوس SLA + Badge فراتر از مهلت).
2. پرونده فروشنده: همه اطلاعات + تاریخچه تغییرات + تطبیق شبا با استعلام بانکی.
3. **چک‌لیست ۵ موردی** هر مورد با تیک جدا: (الف) شناسه ملی/ثبت، (ب) شماره شبا، (پ) آدرس واقعی، (ت) نوع فعالیت، (ث) لوگو و تصاویر + مقایسه نوع ادعاشده با مدارک.
4. ثبت یکی از ۴ تصمیم: **تأیید / رد / نقص اطلاعات / نیاز به بازبینی** — دلیل برای «رد» و «نقص» اجباری؛ هر تصمیم ← `audit_logs` (کاربر، زمان، IP، دلیل).
5. «نقص اطلاعات» ← **مهلت ۷ روز** + لیست موارد ناقص؛ کرون روزانه: پس از ۷ روز بدون تکمیل ← **رد خودکار** + امکان ثبت مجدد.
6. یادآوری خودکار به ادمین پس از «بیش از ۷ روز بدون پاسخ» + SLA یادآوری ۷ روز (ماده ۳ بند ۲ قرارداد).
7. اتصال کانال اعلان (پوش + پیامک + ایمیل با متن قالب‌بندی‌شده) روی mock.

| خروجی مرحله | صف ادمین + چک‌لیست + کرون رد خودکار ۷ روزه |
| معیار قبولی | ردیف `audit_logs` برای هر تصمیم ساخته شود؛ اجرای شبیه‌سازی‌شده کرون ← `REJECTED` |

### M-04.4 — پنل فروشنده پایه + آدرس نسخه‌بندی‌شده (روز D6-D7)
1. صفحه `seller-dashboard.png` با ۴ کارت پایه و حالت خالی «هنوز فروشی نداشته‌اید» + راهنما.
2. «پروفایل فروشگاه»: نام/لوگو/نوع فعالیت/ساعت کاری؛ نمایش جدول تصمیم (مجاز = فعال، غیرمجاز = خاکستری + دلیل).
3. «آدرس ثبتی فروشگاه»: ایجاد نسخه جدید ← `verified_at` خالی + پیام **«پس از تأیید، تغییر نیازمند بررسی مجدد است»**؛ تا تأیید، نسخه قبلی نمایش داده می‌شود.
4. قفل: فروشنده دارای سفارش در جریان ← تغییر آدرس تا تحویل همه سفارش‌ها معلق.
5. صفحه ادمین ۱۱: مقایسه نسخه قدیم/جدید + تأیید/رد + تاریخچه نسخه‌ها.
6. تغییر نوع فعالیت توسط فروشنده ← بازگشت به «در انتظار تأیید» + حذف موقت سرویس‌های ناسازگار.

| خروجی مرحله | ۳ صفحه پنل فروشنده + ۱ صفحه ادمین آدرس + API نسخه |
| معیار قبولی | سناریوی دستی ۶ و ۷ بخش ۴ سبز شود |

### M-04.5 — تأیید نهایی، سطح «تازه‌کار»، تست و Swagger (روز D8)

## ۴. روش تست و پذیرش (Definition of Done)

**تست خودکار (نام فایل‌ها):**
`seller.type-combo.spec.ts` (فقط ۲ ترکیب مجاز) · `seller.docs-matrix.spec.ts` (مدارک هر نوع) · `seller.license-gate.spec.ts` (پروانه الزامی) · `seller.status-machine.spec.ts` (۶ وضعیت + گذارهای ممنوع) · `seller.deficiency-deadline.spec.ts` (۷ روز ← رد خودکار) · `seller.decision-reason.spec.ts` (دلیل اجباری رد/نقص) · `seller-address.versioning.spec.ts` (نسخه + سقف ۳ + قفل سفارش) · `admin.seller-applications.contract.spec.ts`

**سناریوی دستی گام‌به‌گام:**
1. ورود با شماره تستی ← «تکمیل پروفایل» ← انتخاب نقش «فروشنده» ← «ساخت حساب» ← مشاهده **«ثبت‌نام شما در انتظار تأیید ادمین است»** + دکمه «بازگشت به خانه».
2. شروع ثبت‌نام نوع «کلینیک» بدون بارگذاری پروانه ← دکمه ارسال بلوکه + **«پروانه فعالیت الزامی است»** (**پیوست ب قرارداد، سناریو ۲**).
3. انتخاب هم‌زمان «پت‌شاپ + گرومر» (ترکیب غیرمجاز) ← 400 `VALIDATION_ERROR`؛ سپس «پت‌شاپ + کلینیک» ← پذیرش.
4. شبا نامعتبر ← **«شماره شبا معتبر نیست»**؛ کد ملی ۹ رقمی ← **«کد ملی ۱۰ رقم است»**؛ کد پستی ← **«کد پستی ۱۰ رقم است»**.
5. ورود ادمین ← صفحه ۷ «صف تأیید فروشندگان» ← باز کردن پرونده ← تیک ۵ مورد چک‌لیست.
6. تصمیم «نقص اطلاعات» بدون دلیل ← 400 `VALIDATION_ERROR`؛ با دلیل ← اعلان + مهلت ۷ روز + لیست موارد ناقص.
7. شبیه‌سازی ۷ روز (تغییر `created_at` در staging) ← اجرای کرون ← وضعیت `REJECTED` + امکان ثبت مجدد.
8. تصمیم «تأیید» ← فعال‌سازی پنل + سطح «تازه‌کار» + بنر مهلت ۷ روز ثبت اولین محصول + ردیف `audit_logs`.
9. فروشنده «آدرس ثبتی» را ویرایش می‌کند ← نسخه جدید «در انتظار تأیید» و نسخه قبلی همچنان نمایش داده می‌شود؛ ادمین در صفحه ۱۱ تأیید می‌کند ← `version` ۱+.
10. فروشنده نوع فعالیت را عوض می‌کند ← بازگشت به «در انتظار تأیید» + حذف موقت سرویس‌های ناسازگار.
11. فروشنده تأییدنشده `POST /listings` (SP-05) را صدا می‌زند ← 403 `FORBIDDEN_ROLE`.

**خطاهای پرتکرار:**

| کد | HTTP | معنی | مکان پرتکرار |
|----|------|------|--------------|
| `VALIDATION_ERROR` | 400 | فیلد/ترکیب/مدرک نامعتبر | شبا، ترکیب غیرمجاز، تصمیم بدون دلیل |
| `TOKEN_EXPIRED` | 401 | توکن منقضی | نشست ادمین ۱۰ دقیقه‌ای |
| `FORBIDDEN_ROLE` | 403 | نقش مجاز نیست | فروشنده روی `/admin/**` |
| `NOT_FOUND` | 404 | شناسه ناموجود | `application_id` اشتباه |
| `ORDER_STATE_CONFLICT` | 409 | تداخل وضعیت | ویرایش آدرس با سفارش در جریان |
| `RATE_LIMIT_EXCEEDED` | 429 | سقف نرخ | بارگذاری مکرر مدارک |
| `INTERNAL_ERROR` | 500 | خطای داخلی | شکست آپلود MinIO |
