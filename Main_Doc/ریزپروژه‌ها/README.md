> تهیه: ۱۴۰۵/۰۷/۱۶ (۸ اکتبر ۲۰۲۶) — وضعیت: نسخه ۱.۰
> مبانی (ترتیب اعتبار): `قرارداد برنامه نویس/قرارداد-همکاری-برنامه‌نویس.md` ← `Technical Architecture/Technical-Architecture.md` ← `Proposal/Proposal.md` ← `project-document.md` ← `wireframes/` + `PLAN-EXECUTION-LEAN.md`
> هدف: هر زیرپروژه (SP) آن‌قدر مشخص باشد که **بدون کمک هوش مصنوعی هم قابل اجرا، تست و تحویل باشد** — دقیقاً طبق درخواست کارفرمای ۱۴۰۵/۰۷/۱۵.

## ۱. قواعد بازی (ثابت برای همه SPها)

1. **ترتیب:** SPها به‌ترتیب شماره اجرا می‌شوند، مگر جایی که نقشه وابستگی (بخش ۴) موازی‌کاری مجاز داده باشد.
2. **کیفیت دروازه‌ای (Gate):** هیچ SP بعدی شروع نمی‌شود تا بخش «پذیرش» SP قبلی سبز شده باشد. استثنا: SPهایی که نقشه وابستگی آن‌ها را موازی اعلام کرده.
3. **عمودی بودن هر SP:** هر زیرپروژه یک **برش عمودی کامل** است = بک‌اند (endpoint + جدول) + صفحات مرتبط اپ Flutter + صفحات مرتبط پنل وب + تست. هیچ SPای فقط «بک‌اند» یا فقط «اپ» نیست.
4. **صف ادمین در همان SP:** هر SP که صف تأیید/بازبینی داشته باشد، صفحه ادمینی آن را هم در همان SP می‌سازد (SP-15 فقط داشبورد/گزارش/نقش‌ها/تنظیمات نهایی است).
5. **قرارداد API:** همه endpointها زیر `/api/v1`، پاسخ `{success,data,meta}` / `{success:false,error{code,message,details,request_id}}`، خطاها فارسی دقیقاً از بخش «متون دقیق رابط کاربری» project-document.
6. **مالی:** `NUMERIC(18,0)`، `Idempotency-Key` در `POST /payments`، هیچ retry خودکار مالی، soft-delete + `audit_logs`.
7. **تصمیم معماری اجرایی (مهم):** طبق `PLAN-EXECUTION-LEAN.md` اجرای عملی روی **مونولیت ماژولار NestJS** انجام می‌شود (schema جدا per ماژول، مرز سخت، بدون join بین‌ماژولی) — نه ۱۲ استقرار جدا. نام جداول و `/api/v1` دقیقاً مطابق Technical Architecture حفظ می‌شود تا استخراج سرویس در آینده بدون بازنویسی باشد.
   ⚠️ **اگر قرارداد را امضا کرده‌اید:** ماده ۲ قرارداد «۱۲ میکروسرویس» را نوشته — پیش از شروع SP-00 یک **الحاقیه کتبی کوچک** (مونولیت ماژولار + مسیر استخراج) اضافه کنید، وگرنه نقض ماده ۷ است. اگر هنوز امضا نشده، همین متن را در ماده ۲ جایگزین کنید.
8. **حذف‌شده‌های موقت (از SPها غایب‌اند):** رزرو نوبت، ویزیت آنلاین، بیمه، حامی کارت، پت‌تکسی، کافه، پانسیون، گرومینگ، دام بزرگ، BNPL، Elasticsearch، چت realtime سنگین. جداول و API این‌ها **رزرو** می‌شوند ولی پیاده نمی‌شوند.


- **موازی مجاز:** SP-02 ∥ SP-03 (هر دو بعد از SP-01) — کارفرما روی SP-03 تمرکز کند، توسعه‌دهنده SP-02 را هم ببرد.
- **موازی مجاز:** SP-03 ∥ SP-04 (هر دو بعد از SP-01) — وابستگی SP-04 به SP-03 فقط زمان‌بندی/سازمانی است (سرفصل SP-04 هنوز «بعد از SP-03» را نقل می‌کند)؛ فنی‌اً SP-04 فقط به SP-01 نیاز دارد و هر دو به SP-05 می‌رسند.
- **موازی مجاز:** SP-11 تا SP-14 بعد از SP-08 قابل شروع‌اند (لازم نیست SP-09/SP-10 تمام شود).
- **مقدار:** SP-05 بعد از SP-03 و SP-04 شروع می‌شود (تأیید محصول به هر دو نیاز دارد).

**ترتیب کامل اجرایی (نسخه ساده و بدون ابهام):**
`SP-00 → SP-01 → SP-02 و SP-03 و SP-04 → SP-05 → SP-06 → SP-07 → SP-08 → SP-09 → SP-10 → SP-11 → SP-12 → SP-13 → SP-14 → SP-15 → SP-16` (به‌جز موازی‌های مجاز بالا؛ SP-02/SP-03/SP-04 هر سه بعد از SP-01 قابل شروع‌اند). تا زمانی که SP قبلی بخش «پذیرش» خود را سبز نکرده، SP بعدی عملاً شروع نمی‌شود — منبع حقیقت، پانویس «وابستگی» در همان فایل SP است؛ این نمودار فقط کمک‌بصری است.

## ۳. ساختار ثابت هر فایل SP (الزامی)

هر `SP-XX.md` دقیقاً پنج بخش دارد:

| بخش | جواب می‌دهد به خواسته کارفرما |
|-----|------------------------------|
| **۱. هدف، Deliverable، خارج از اسکوپ** | «deliver و خروجی‌ش چیه» |
| **۲. پیش‌نیازهای فنی** | «پیش‌نیازهای فنی‌ش مشخص باشه از قبل» |
| **۳. اقدامات و مراحل با Milestone** | «تمام اقدامات و مراحلش مشخص و با milestone باشه» |
| **۴. روش تست و پذیرش (DoD)** | «چجوری باید اون خروجی رو تست کرد» |
| **۵. زمان‌بندی و تقسیم کار + ریسک** | «زمان‌بندی هر پروژه کوچک مشخص باشه» |

نقش‌ها (از `PLAN-EXECUTION-LEAN.md` بخش ۵):
- **کارفرما (تو):** اجرا روی سخت‌افزار خودش (`docker compose up`، `flutter run`)، تست دستی روی گوشی، تصمیم محتوایی/قیمت تستی، تأمین اکانت‌ها (GitHub، دامنه، درگاه، پیامک)، بازخورد در ≤۳ روز کاری.
- **توسعه‌دهنده/AI:** کد، SQL مهاجرت، تست قرارداد، Swagger، رفع باگ.
