## ۱. هدف، Deliverable و خارج از اسکوپ

**هدف:** بستن کامل مسیر «شماره موبایل → OTP → JWT/Refresh → پروفایل → نقش‌ها → نشست‌ها → حذف حساب» به‌عنوان دروازه ورود همه SPهای بعد؛ خروجی باید بدون کمک هوش مصنوعی هم قابل اجرا، تست و تحویل باشد.

| دسته | Deliverable دقیق |
|------|-------------------|
| جداول (migration `002-user-auth`) | ساخت **روی** `001-auth-user` پایه SP-00 — ۵ جدول `users, user_roles, otp_codes, sessions, audit_logs` از قبل هستند و از نو ساخته نمی‌شوند (**تصمیم**)؛ افزوده‌های این SP: `terms_acceptances` (فقط جدول — endpoint قوانین در SP-02، **تصمیم**)، `permissions`، `role_permissions`، ستون‌های `users.two_factor_enabled` و `users.deletion_scheduled_at` + ایندکس `otp_codes(phone,purpose,expires_at)` و `sessions(user_id,revoked_at)`؛ قواعد SP-00: `id UUIDv7`، `created_at/updated_at` ISO 8601، soft delete با `deleted_at` |
| Endpointهای Auth (`/api/v1`) | `POST /auth/otp/request`، `POST /auth/otp/verify`، `POST /auth/refresh`، `POST /auth/logout` (مسیرهای ثابت §۶.۵ — **تصمیم:** `/auth/refresh` و `/auth/logout` طبق project-document §۸، نه `/auth/otp/refresh` خلاصه‌شده TA) |
| Endpointهای User | `GET /me`، `PATCH /me`، `POST /me/delete-request`، `POST /me/delete-request/cancel` (تصمیم؛ برای سناریوی ۸ «انصراف از حذف»)، `GET /me/sessions`، `POST /me/sessions/{id}/revoke` و `POST /me/sessions/revoke-all` (تصمیم؛ دکمه «خروج از همه دستگاه‌ها») |
| RBAC | جدول `permissions` + `role_permissions` + seed **۸ نقش** (مشتری، فروشنده، ارائه‌دهنده خدمت، ادمین/Super، اپراتور پشتیبانی، اکانتنت، مالی، مدیر محتوای سلامت) + Guard سراسری (`@RequirePermission`) + ماتریس مبتنی بر `project-document.md:1342` + **ثبت `audit_logs` روی تغییر نقش** + باطل شدن نشست‌های فعال هنگام تغییر نقش (سناریوی ۳ RBAC) — ⚠️ «پیک» عمداً نقش نیست |

| نشست | `sessions` با `refresh_token_hash` (چرخشی، ۳۰ روز) + تشخیص دستگاه با `X-Device-Id`/`X-Platform` + پیامک `SMS-NEW-DEVICE` در ورود از دستگاه جدید + لیست نشست‌ها و ابطال |
| حذف حساب | درخواست با دلیل اجباری + تأیید OTP → پیش‌بررسی ۹ مانع → `PENDING_DELETION` ۱۴ روزه (خواندنی/غیرنوشتنی) → انصراف → کرون شبانه ۰۳:۰۰ حذف نهایی/ناشناس‌سازی + قالب `SMS-ACCOUNT-DELETE` |
| صفحات اپ Flutter | `login.png` («به AMPET خوش آمدید»، ورود کد ۵خانه با تایمر ۱۲۰ ثانیه)، «تکمیل پروفایل» («چند اطلاعات دیگر تا تکمیل ثبت‌نام»)، «نشست‌ها/دستگاه‌ها»، «درخواست حذف حساب» + دیالوگ «نشست شما پایان یافت» |
| تست + مستندات | unit + integration + contract طبق §۴؛ Swagger از کد در `/docs` برای همه endpointهای بالا با پاسخ `{success,data,meta}` / `{success:false,error{code,message,details,request_id}}` |

**خارج از اسکوپ (به SPهای دیگر):**
- آدرس‌ها، پرونده حیوان، واکسن/اشتراک → **SP-02**؛ endpointهای `GET /terms`، `POST /terms/accept`، `GET /me/terms` → **SP-02** (اینجا فقط جدول `terms_acceptances` و ستون `users.terms_version` می‌نشیند).
- صفحات پنل ادمین (لیست نقش‌ها، ویرایش ماتریس، لاگ اقدامات، تأیید دوم مالی، کدهای پشتیبان 2FA) → **SP-15**؛ اینجا فقط Guard، seed، endpointهای احراز و لاگ.
- فعال‌سازی نقش «فروشنده» پس از تأیید ادمین، `SUSPENDED` کردن فروشنده → **SP-04** (اینجا فقط ستون `users.status` و اثرش روی ورود).
- اتصال واقعی SMS/Push → **SP-11**؛ اینجا فقط کانال mock SP-00 با قالب‌های `SMS-OTP`، `SMS-OTP-RESEND`، `SMS-NEW-DEVICE`، `SMS-REGISTER`، `SMS-2FA`، `SMS-ACCOUNT-DELETE`.
- موانع حذف وابسته به ماژول‌های دیگر (سفارش، مرجوعی، تیکت، اعتبار، کیف پول، امتیاز، پنل فروشنده، حامی کارت، برداشت بانکی) → اتصال در SPهای مالک؛ اینجا فقط **registry موانع** (بند M-01.۵).
- اعلان ایمیل `MAIL-DELETE` → SP-11 (پیامک + In-App کافی برای پذیرش این SP است).

## ۳. اقدامات و مراحل (گام‌به‌گام با Milestone)

### M-01.۱ — گسترش اسکیمای Auth و User (روز ۱)
1. `docker compose up -d postgres redis` را بالا بیا و `npm run db:migrate` پایه SP-00 (`001-auth-user`) را اجرا کن تا ۵ جدول Auth/User ساخته شود.
2. migration `002-user-auth` بنویس: `CREATE` برای `terms_acceptances, permissions, role_permissions` با ستون‌های `project-document.md:4849` + `ALTER` روی `users` برای `two_factor_enabled` و `deletion_scheduled_at` + ایندکس‌های `otp_codes(phone,purpose,expires_at)` و `sessions(user_id,revoked_at)`؛ `users.status` سه مقدار `ACTIVE | PENDING_DELETION | SUSPENDED` + `DELETED` فقط پس از اجرای حذف نهایی (تصمیم؛ ستون `status` در `001-auth-user` هست و فقط CHECK به آن اضافه می‌شود).
3. seed: ۸ نقش + ماتریس `role_permissions` از جدول `project-document.md:1342-1366` + کاربر ادمین اولیه (شماره‌اش از `.env`) + کتابخانه `permissions` مطابق ماتریس (نقش «پیک» ندارد).
4. `up→down→up` را در staging اجرا کن.
**خروجی:** migration `002-user-auth` + سیدها + ERD به‌روز. **معیار قبولی:** rollback بدون خطا، `SELECT` روی هر ۳ جدول جدید ستون‌های ERD را دارد و ۵ جدول `001-auth-user` دست‌نخورده می‌مانند.

### M-01.۲ — OTP request/verify + سقف‌ها (روز ۲-۳)
1. `POST /auth/otp/request`: اعتبار شماره (ایرانی ۱۱ رقم، پیش‌شماره ۰۹) → سقف **۳ درخواست در ۱۰ دقیقه به تفکیک هر شماره و هر IP** → صدور کد **۵ رقمی** با `expires_at = now + 120s` در `otp_codes` (بدون ذخیره متنی؛ هش + purpose) → ارسال با قالب `SMS-OTP`؛ برای ارسال مجدد `SMS-OTP-RESEND` (کد قبلی بلافاصله باطل).
2. `POST /auth/otp/verify`: اعتبار، انقضا (`OTP_EXPIRED`)، شمارش تلاش؛ **۳ تلاش ناموفق → قفل ۱۵ دقیقه** (`OTP_TRIES_EXCEEDED` + هدر `Retry-After: 900`) با پیام «تلاش بعدی بعد از ۱۵ دقیقه»؛ موفق → ساخت/پیدا کردن `users`، صدور JWT ۱۵ دقیقه + refresh ۳۰ روزه چرخشی، فیلد `is_new_user` برای مسیر «تکمیل پروفایل».
3. شماره مسدود (`users.status = SUSPENDED` یا لیست بلک‌لیست): پاسخ `403 ACCOUNT_BLOCKED` با پیام عمومی «امکان ورود برای این شماره وجود ندارد» + لینک پشتیبانی — **بدون ذکر دلیل** (سناریوی ۵).
4. قالب `SMS-REGISTER` فقط برای اولین ثبت‌نام موفق.
**خروجی:** ماژول `auth` (OTP). **معیار قبولی:** تست‌های `otp_*` §۴ سبز + سناریوی UAT پیوست ب #۱ (بلاک چهارم درخواست با پیام فارسی).

### M-01.۳ — JWT، Refresh چرخشی و نشست‌ها (روز ۳-۴)
1. Access JWT **۱۵ دقیقه** (ادمین **۱۰ دقیقه**) با claim های `sub, role, sid, iat, exp`؛ هدر `Authorization: Bearer` + الزام `X-Device-Id` و `X-Platform` در ورود.
2. `POST /auth/refresh`: refresh **۳۰ روزه چرخشی** — هر بار refresh کهنه باطل و ردیف `sessions` به‌روزرسانی می‌شود؛ استفاده مجدد از refresh قدیمی = رد کل دستگاه (`401 TOKEN_INVALID`) و ثبت رویداد امنیتی.
3. `POST /auth/logout`: باطل کردن refresh همان نشست (بدون خطا اگر از قبل باطل است).
4. ورود از دستگاه جدید (مقایسه `device_id` با نشست‌های فعال) → ارسال `SMS-NEW-DEVICE` + اعلان In-App با دکمه «خروج از همه دستگاه‌ها» (`POST /me/sessions/revoke-all`).
5. `GET /me/sessions`: نام دستگاه، پلتفرم، آخرین فعالیت، «این دستگاه»؛ `POST /me/sessions/{id}/revoke`.
6. اگر `users.status = PENDING_DELETION` باشد ورود مجاز است ولی `GET /me` پرچم `deletion_pending_until` می‌دهد (سناریوی ۸).
**خروجی:** ماژول `session`. **معیار قبولی:** تست‌های `session_*` سبز؛ refresh قدیمی بعد از چرخش رد می‌شود.

### M-01.۴ — پروفایل، RBAC و 2FA اسکلت (روز ۴-۶)
1. `PATCH /me` (نام/نام خانوادگی الزامی در اولین تکمیل — «نام و نام خانوادگی الزامی است») + `GET /me` شامل `role, status, terms_version, referral_code, last_seen_at`.
2. تکمیل پروفایل نامعتبر = `422 TERMS_NOT_ACCEPTED` تا وقتی ردیف `terms_acceptances` برای نسخه فعال ثبت شده باشد؛ ثبت نشست/زمان/IP/دستگاه در همان ردیف (قابل استناد).
3. Guard سراسری `@RequirePermission` + ماتریس ۸ نقش؛ خطا `403 FORBIDDEN_ROLE` یا پیام UI «سطح دسترسی ناکافی»؛ تلاش مستقیم مسیر ممنوع = ثبت در `audit_logs`.
4. تغییر نقش کاربر (`PATCH /admin/users/{id}/role` — این SP فقط endpoint، صفحه وب در SP-15): اعتبارسنجی نقش مبدأ/مقصد → ثبت `audit_logs` با `before/after` → **باطل شدن فوری همه نشست‌های فعال کاربر** (سناریوی ۳ RBAC) → `audit_logs` فقط‌افزودنی است (سناریوی ۴).
5. اسکلت 2FA: ادمینِ مالی/Super پس از OTP پاسخ `401 2FA_REQUIRED` می‌گیرد؛ `POST /admin/auth/2fa/verify` با کد ۱۲۰ ثانیه‌ای قالب `SMS-2FA` → صدور JWT ادمین ۱۰ دقیقه؛ `/admin/**` بدون آن `403`.
**خروجی:** ماژول `rbac` + پروفایل. **معیار قبولی:** تست‌های `rbac_*` سبز و `SELECT` روی `audit_logs` برای هر تغییر نقش یک ردیف دارد.

### M-01.۵ — حذف حساب ۱۴ روزه (روز ۶-۷)
1. `POST /me/delete-request`: فرم با **دلیل اجباری از منو** + توضیح اختیاری + **تأیید با OTP**.
2. پیش‌بررسی خودکار از طریق **registry موانع** (۹ ردیف `project-document.md:2976-2988`): سفارش در جریان، درخواست مرجوعی باز، تیکت باز، بدهکاری اعتباری (مسدود قطعی)، موجودی کیف پول (هشدار)، امتیازات فعال (هشدار)، پنل فروشنده فعال، حامی کارت فعال، برداشت بانکی در انتظار. **تصمیم:** هر ماژول بعد از تحویل، چک خودش را ثبت می‌کند؛ تا آن زمان چکِ بی‌داده برمی‌گرداند و پاسخ `422 ACCOUNT_DELETION_BLOCKED` با لیست موانع + لینک رفع هر مورد («سفارش {n} در جریان دارد — تا {تاریخ} منتظر بمانید»).
3. بدون مانع → وضعیت `PENDING_DELETION` + `deletion_scheduled_at = now + 14 days` → اعلان پیامک/In-App با لینک انصراف (`SMS-ACCOUNT-DELETE`) + یادآوری روزهای ۳، ۱۰ و ۱۳ (ساختار ردیف‌ها؛ ارسال واقعی در SP-11).
4. طی ۱۴ روز: داده‌ها خواندنی، نوشتنی؛ `POST /me/delete-request/cancel` با کد تأیید → بازگشت کامل به `ACTIVE`.
5. کرون شبانه **۰۳:۰۰**: حذف/ناشناس‌سازی نام، آدرس، شبا، عکس پروفایل، دستگاه‌ها، متن نظرها («کاربر محترم») + نگه‌داشتن شماره به‌صورت **هش یک‌طرفه** برای جلوگیری از ثبت‌نام تکراری + استثناهای نگهداری ۵ ساله (مالی → SP-07/SP-09) + ایمیل/پیامک پایانی؛ ثبت‌نام مجدد همان شماره فقط پس از **۳۰ روز**.
**خروجی:** سرویس `account-deletion` + کرون. **معیار قبولی:** تست‌های `deletion_*` سبز؛ شبیه‌سازی «درخواست در روز صفر → انصراف → درخواست دوباره → اجرای کرون در روز ۱۴» روی دیتابیس تستی.

### M-01.۶ — صفحات اپ، تست، تحویل (روز ۷-۸)
1. `login.png`: عنوان «به AMPET خوش آمدید»، اعتبار «شماره موبایل معتبر نیست. ۱۱ رقم وارد کنید»، صفحه «کد تأیید را وارد کنید» با ۵ خانه + تایمر ۱۲۰ ثانیه + «ارسال مجدد کد»، خطاها: «کد اشتباه است. ۲ تلاش دیگر دارید»، «کد منقضی شده است. کد جدید درخواست کنید»، «تعداد درخواست‌های شما زیاد است. {دقیقه} دقیقه دیگر دوباره تلاش کنید».
2. صفحه «چند اطلاعات دیگر تا تکمیل ثبت‌نام» (نام + چک‌باکس قوانین + انتخاب نقش اختیاری فروشنده → پیام «ثبت‌نام شما در انتظار تأیید ادمین است»)؛ صفحه نشست‌ها؛ صفحه «درخواست حذف حساب» با شمارش معکوس و دکمه «انصراف از حذف»؛ دیالوگ «نشست شما پایان یافت» ← «برای امنیت بیشتر دوباره وارد شوید» با حفظ مسیر/فرم پس از ورود.
3. RTL کامل، ارقام فارسی، text-scale ۱۳۰٪، تاچ ≥۴۴dp، دکمه ۴۸dp.
4. `npm run test` + `flutter test` + contract testها + تولید Swagger و چک دستی `/docs`؛ صورت‌جلسه تحویل M1.
**خروجی:** ۴+ صفحه اپ + گزارش تست + Swagger. **معیار قبولی:** DoD بخش ۴ صددرصد تیک‌خورده.

## ۴. روش تست و پذیرش (DoD)

**تست خودکار (نام تست‌ها):** `otp_request_rate_limited_3_per_10min_per_phone_and_ip`، `otp_verify_success_issues_jwt15_and_refresh30_rotation`، `otp_wrong_code_counts_and_locks_15min_with_retry_after_900`، `otp_expired_code_rejected`، `otp_resend_invalidates_previous_code`، `blocked_phone_returns_generic_account_blocked`، `refresh_rotation_reuse_old_token_revokes_session`، `logout_revokes_refresh_only`، `new_device_triggers_sms_new_device`، `me_sessions_list_and_revoke_and_revoke_all`، `admin_jwt_expires_10min_customer_15min`، `admin_without_2fa_gets_2fa_required`، `forbidden_role_returns_403_and_audit_row`، `role_change_revokes_active_sessions_and_writes_audit_before_after`، `profile_requires_terms_acceptance`، `delete_request_requires_reason_and_otp`، `delete_blocked_by_active_order_422`، `delete_cancel_restores_active`، `nightly_job_at_0300_anonymizes_and_keeps_phone_hash`، `re_register_same_phone_allowed_after_30days`، `public_rate_limit_60_per_min_admin_120_per_min`.

**سناریوی دستی گام‌به‌گام (👤 کارفرما روی گوشی):**
1. **ورود:** شماره معتبر → «کد تأیید را وارد کنید» با تایمر ۱۲۰ ثانیه؛ کد را از لاگ کانال mock کپی کنید → ورود موفق.
2. **۳ درخواست/۱۰ دقیقه (UAT #۱):** بار چهارم → پیام «تعداد درخواست‌های شما زیاد است. {دقیقه} دقیقه دیگر دوباره تلاش کنید» + شمارش معکوس واقعی.
3. **۳ کد اشتباه:** «کد اشتباه است. ۲ تلاش دیگر دارید» → در سومی قفل ۱۵ دقیقه + شمارش معکوس روی دکمه.
4. **کد منقضی:** ۱۲۱ ثانیه صبر کنید → «کد منقضی شده است. کد جدید درخواست کنید».
5. **کاربر جدید:** ورود → «چند اطلاعات دیگر تا تکمیل ثبت‌نام» → نام + پذیرش قوانین → «ساخت حساب» → پیامک `SMS-REGISTER`.
6. **چند دستگاه:** ورود از گوشی دوم → پیامک `SMS-NEW-DEVICE` → «ورود جدید از {دستگاه}» + دکمه «خروج از همه دستگاه‌ها» → دستگاه اول از کار می‌افتد.
7. **تغییر نقش:** در DB یا از طریق `PATCH /admin/users/{id}/role` نقش یک کاربر را عوض کنید → نشست فعال او باطل و `audit_logs` ردیف `before/after` دارد.
8. **حذف حساب:** پروفایل ← «حذف حساب» → دلیل اجباری + OTP → «درخواست حذف حساب شما ثبت شد. تا {تاریخ} امکان انصراف دارید» → ورود مجدد = «حساب شما در انتظار حذف است» + «انصراف از حذف» → انصراف → حساب فعال.
9. **اجرای کرون:** تاریخ `deletion_scheduled_at` را قدیمی کنید و کرون ۰۳:۰۰ را اجرا → نام/آدرس/عکس پاک، شماره هش‌شده، پیامک پایانی.
10. **ورود آفلاین:** هواپیمایی → «اتصال اینترنت برقرار نیست»؛ پس از اتصال ارسال مجدد ممکن است.
