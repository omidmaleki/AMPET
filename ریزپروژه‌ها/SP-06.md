## ۳. اقدامات و مراحل (گام‌به‌گام با Milestone)

### M-06.۱ — اسکیمای سبد و سفارش (روز ۱-۲)
1. `docker compose up -d postgres redis` را از ریشه ریپو بالا بیاور و `npm run migration:run` را یک‌بار اجرا کن تا مهاجرت پایه SP-05 تأیید شود.
2. migration جدید `sp06_cart_order` برای `carts, cart_items, orders, order_items, cancellations` بنویس (فقط نام جداول و ستون‌های ERD `project-document.md:4794-4807`).
3. قواعد سراسری را اعمال کن: مبلغ `NUMERIC(18,0)` (هرگز FLOAT)، `id UUIDv7`، `deleted_at`، ایندکس `orders(user_id,status)`؛ `order_items.snapshot` شامل نام/SKU/قیمت/فروشنده/نسخه آدرس ثبتی در لحظه ثبت.
4. rollback را در staging اجرا کن: `npm run migration:down` سپس دوباره `up`.
**خروجی:** ۲ فایل migration + ERD به‌روزشده. **معیار قبولی:** `up→down→up` بدون خطا و `SELECT` روی ۵ جدول ستون‌های ERD را دارد.

### M-06.۲ — سبد خرید و چرخه عمر Hold (روز ۲-۴)
1. endpointهای سبد (`GET /cart` تا `POST /cart/items/{id}/hold`) را با اعتبارسنجی سرور بساز؛ سبد گروه‌بندی بر اساس فروشنده (هر فروشنده یک بلوک).
2. تایمر را پیاده کن: افزودن به سبد = **۱۵ دقیقه** (عادی) / **حداکثر ۵ دقیقه** (شلوغ)؛ ورود به چک‌اوت = تمدید تا **۲۰ دقیقه** + re-validate؛ کلیک «پرداخت» = تمدید تا **۳۰ دقیقه** + اعتبارسنجی نهایی **پیش از باز شدن درگاه**.
3. حالت شلوغ: کلید دستی ادمین + فعال‌سازی خودکار اگر در ۵ دقیقه اخیر بیش از N سفارش ثبت شده؛ هنگام تعویض، push «به دلیل حجم بالا، مهلت رزرو سبد شما ۵ دقیقه شد» به همه سبدهای فعال.
4. Job آزادسازی هر **۳۰ ثانیه** (بستن holdهای منقضی + آزادسازی موجودی) و شمارش معکوس در `GET /cart/hold-status`؛ push «نزدیک شدن به انقضای نگه‌داری سبد (۲ دقیقه مانده)».
5. `POST /cart/validate` رفتار نبود موجودی **پیش از درگاه** را اجرا کن: جلوی باز شدن درگاه گرفته شود → پیام دقیق «موجودی این کالا به پایان رسیده است» + نام کالا → خروج خودکار آیتم از سبد یا علامت «ناموجود» (به انتخاب کاربر) → پیشنهاد کالای جایگزین از همان فروشنده و سایر فروشندگان → صدور خودکار **کوپن عذرخواهی ۵٪ با اعتبار ۷ روزه** → گزینه «اطلاع‌رسانی موجودی» (ثبت شماره → پوش+پیامک هنگام موجود شدن) → اگر سبد خالی شد پرداخت غیرفعال + دکمه «بازگشت به سبد».
**خروجی:** ماژول `cart` + Job ۳۰ ثانیه‌ای. **معیار قبولی:** تست‌های `hold_*` و `stockout_*` §۴ سبز + پیام‌های فارسی دقیقاً مطابق UI Copy.

### M-06.۳ — چک‌اوت و ثبت سفارش چندفروشگاهی (روز ۴-۶)
1. `POST /checkout/preview`: آدرس + بازه + هزینه ارسال هر فروشگاه + جمع هر بلوک + جمع کل؛ re-validate موجودی و تمدید hold تا ۲۰ دقیقه.
2. بازه تحویل S1-S5 (S1 ۰۹:۰۰-۱۲:۰۰، S2 ۱۲:۰۰-۱۵:۰۰، S3 ۱۵:۰۰-۱۸:۰۰، S4 ۱۸:۰۰-۲۱:۰۰، S5 ۲۱:۰۰-۲۳:۰۰): اگر برای همه فروشگاه‌های سبد مشترک بود یک انتخاب، وگرنه تفکیک بازه به هر سفارش؛ تغییر بازه رایگان تا «تحویل به پیک» و حداکثر **۲ بار** در هر سفارش.
3. `POST /orders`: اعتبارسنجی نهایی قبل از باز کردن درگاه (ناموفق = `422 STOCK_UNAVAILABLE` / `409 HOLD_EXPIRED` و درگاه باز نمی‌شود) → ساخت **N سفارش مستقل** (یکی برای هر فروشنده) با `checkout_group` یکسان، هزینه ارسال جداگانه به هر سفارش، نسخه آدرس/قیمت/کالا snapshot، وضعیت «در انتظار پرداخت»؛ **یک پرداخت یکجا** در SP-07 همین گروه را می‌پوشاند.
4. تأیید/رد/لغو فروشنده و تایم‌لاین وضعیت‌ها را وصل کن: «ثبت شده» ← «تأیید شده» ← «در حال آماده‌سازی» ← «تحویل پیک» ← «در حال ارسال» ← «تحویل شده» + «لغو شده»/«مرجوع شده»؛ عدم تأیید فروشنده تا **۲۴ ساعت** → لغو خودکار + بازگشت کامل + اعلان.
**خروجی:** endpoint ثبت سفارش + پنل فروشنده. **معیار قبولی:** سناریوی UAT پیوست ب #۴ (خرید از ۲ فروشگاه با یک پرداخت) در backend سبز: دقیقاً ۲ ردیف `orders` با یک `checkout_group`.

### M-06.۴ — ماشین لغو سخت‌گیرانه (روز ۶-۸)
1. جدول مجوز لغو را مطابق `project-document.md:2298` به‌صورت قانون در کد پیاده کن (fail = `422 CANCEL_NOT_ALLOWED` با پیام «با این وضعیت سفارش، لغو ممکن نیست»): سبد = حذف کالا؛ «در انتظار پرداخت» = لغو رایگان + **لغو خودکار پس از ۲ ساعت**؛ «پرداخت شده/در انتظار تأیید فروشنده» = **لغو رایگان ۱۰۰٪ شامل هزینه ارسال**؛ «تأیید شده» = فقط «درخواست لغو»؛ «در حال ارسال» = لغو مستقیم ممنوع؛ «تحویل شده» = فقط مرجوعی (SP-10).
2. جریان «درخواست لغو»: دکمه + **دلیل اجباری از منو** + توضیح اختیاری → وضعیت «در انتظار تصمیم فروشنده» (سفارش از لیست فعال خارج نمی‌شود) → اعلان پوش+پیامک+ایمیل → فروشنده **۲۴ ساعت** فرصت: تأیید = لغو نهایی و بازگشت ۱۰۰٪؛ رد = بازگشت وضعیت قبل + «درخواست لغو رد شد»؛ **عدم پاسخ = رد خودکار به نفع فروشنده** → مشتری می‌زند تیکت → **ادمین ۲۴ ساعت** تصمیم می‌گیرد (صفحه ۱۸).
3. لغوهای فروشنده: ۱۰۰٪ بازگشت + **کوپن ۵٪** + **امتیاز منفی ۰٫۵**؛ «برگشت پیک» = ۱۰۰٪ + هزینه رفت‌وبرگشت از حساب فروشنده + کوپن ۵٪ + ۰٫۵−؛ لغو ادمین بدون امتیاز منفی.
4. Jobهای خودکار را بساز: عدم پرداخت ۲ ساعت؛ عدم تأیید فروشنده ۲۴ ساعت؛ عدم پاسخ به درخواست لغو ۲۴ ساعت؛ ناموجود شدن پس از پرداخت = لغو فوری + بازگشت کامل + کوپن ۵٪ + امتیاز منفی فروشنده. همه با `cancellations` (initiator/reason/status/penalty/decided_at) + `audit_logs`.
5. لغو چندفروشگاهی: فقط روی همان سفارش؛ بازگشت فقط مبلغ و هزینه ارسال همان فروشگاه؛ بازه سفارش‌های دیگر دست نمی‌خورد؛ اگر کد تخفیف سبد با لغو از حد نصاب افتاد → باطل و مابه‌التفاوت از بازگشت کم شود.
**خروجی:** سرویس `cancellation` + Jobها + صفحه ادمین. **معیار قبولی:** تست‌های `cancel_*` §۴ سبز و هر تغییر وضعیت ردیف `audit_logs` دارد.

**خروجی:** صفحات وب + گزارش تست + Swagger. **معیار قبولی:** DoD بخش ۴ صددرصد تیک‌خورده.

## ۴. روش تست و پذیرش (DoD)

**تست خودکار (نام تست‌ها):** `cart_add_creates_hold_15min`، `cart_peak_mode_shortens_hold_to_5min`، `checkout_extends_hold_20min_and_revalidates`، `payment_click_extends_hold_30min_blocks_gateway_on_fail`، `release_job_frees_expired_holds_every_30s`، `stockout_before_gateway_blocks_with_exact_message_and_coupon_5pct_7d`، `stockout_empty_cart_disables_payment`، `multi_store_checkout_creates_n_independent_orders_one_group`، `shipping_fee_is_per_store`، `order_items_snapshot_survives_catalog_change`، `slot_shared_when_common_else_per_order`، `auto_cancel_unpaid_after_2h`، `cancel_free_100pct_before_seller_confirm`، `cancel_request_requires_reason`، `cancel_request_auto_reject_after_24h_no_response`، `admin_decision_within_24h`، `seller_cancel_gives_100pct_plus_coupon5_minus_0_5`، `cancel_affects_only_target_order`، `parallel_last_unit_bought_once_row_lock`.

**سناریوی دستی گام‌به‌گام (👤 کارفرما روی گوشی):**
1. **سبد ۲ فروشگاهه:** افزودن کالا از ۲ فروشنده → در `cart.png` دو بلوک جدا + دو شمارش معکوس دیده شود؛ Toast «به سبد خرید اضافه شد».
2. **چک‌اوت:** ورود به `checkout.png` → پیام «موجودی تا ۲۰ دقیقه برای شما رزرو شد» + انتخاب بازه S2 + دکمه «پرداخت {مبلغ}».
3. **اتمام موجودی پیش از درگاه:** کالایی را از یک ترمینال دیگر ناموجود کنید و در اپ «پرداخت» را بزنید → درگاه باز نشود، پیام «موجودی این کالا به پایان رسیده است — {نام کالا}»، آیتم حذف/ناموجود شود، پیشنهاد جایگزین + کوپن ۵٪ (۷ روزه) + دکمه «اطلاع‌رسانی موجودی» نمایان شود.
4. **UAT پیوست ب #۴:** خرید از ۲ فروشگاه با یک پرداخت → در `orders.png` دقیقاً **۲ سفارش مستقل** با وضعیت و ردیابی جدا؛ دیتابیس: ۲ ردیف `orders`، یک `checkout_group`؛ هزینه ارسال هر فروشگاه جداگانه.
5. **لغو پیش از تأیید:** فروشنده سفارش را تأیید نکرده → «لغو سفارش» → دیالوگ تأیید → بلافاصله لغو + «بازگشت وجه به کیف پول شما واریز شد» (در SP-07) + آزادسازی موجودی.
6. **درخواست لغو پس از تأیید:** تأیید فروشنده → دکمه لغو → فقط «درخواست لغو» با دلیل اجباری → «درخواست لغو ثبت شد» + شمارش ۲۴ ساعت در پنل فروشنده؛ فروشنده رد کند → «درخواست لغو رد شد» + امکان تیکت.
7. **عدم پاسخ فروشنده:** بدون اقدام ۲۴ ساعت (کرون/کلون آزمایشی با `created_at` قدیمی) → رد خودکار به نفع فروشنده + تیکت اختلاف + تصمیم ادمین در صفحه ۱۸.
8. **لغو خودکار ۲ ساعته:** سفارش بدون پرداخت را رها کنید → پس از ۲ ساعت لغو خودکار + «سفارش {شماره} لغو شد» + آزادسازی موجودی.

**جدول خطاهای پرتکرار:**

| code | HTTP | پیام فارسی دقیق | سناریو |
|------|------|----------------|--------|
| `STOCK_UNAVAILABLE` | 422 | «موجودی این کالا به پایان رسیده است» / «موجودی کافی نیست. فقط {n} عدد باقی مانده است» | اعتبارسنجی نهایی پیش از درگاه |
| `HOLD_EXPIRED` | 409 | «مهلت رزرو سبد شما به پایان رسیده است» | تماس `POST /orders` پس از انقضا |
| `ORDER_STATE_CONFLICT` | 409 | «سفارش تازه‌تر شده است. بروزرسانی کنید» | تغییر همزمان وضعیت توسط فروشنده/مشتری |
| `CANCEL_NOT_ALLOWED` | 422 | «با این وضعیت سفارش، لغو ممکن نیست» | لغو مستقیم در «در حال ارسال» |
| `VALIDATION_ERROR` | 400 | «این فیلد الزامی است» / «حداقل یک آدرس لازم است» | بدون آدرس یا بدون دلیل لغو |
| `NOT_FOUND` | 404 | «سفارش یافت نشد» | شناسه نامعتبر |
| `RATE_LIMIT_EXCEEDED` | 429 | هدر `Retry-After` + پیام عمومی | بیش از ۶۰ درخواست/دقیقه |

- [ ] سبد چندفروشگاهی = N سفارش مستقل + یک `checkout_group` (UAT #۴ سبز)

- [ ] ۵ صفحه Flutter + ۳ صفحه فروشنده + ۳ صفحه ادمین با متن‌های دقیق UI Copy
