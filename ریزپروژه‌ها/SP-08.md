## ۱. هدف، Deliverable و خارج از اسکوپ

**هدف:** بستن حلقه تحویل Store-Delivered: فروشنده مرسوله را «در حال ارسال» می‌کند → کد ۶ رقمی تصادفی (فقط هش) با پوش+پیامک برای مشتری → پیک از طریق **لینک وب تک‌سفارش بدون اپ و بدون ثبت‌نام** تحویل ثبت می‌کند (کد صحیح + نام/نسبت گیرنده + عکس اجباری) → رویداد تحویل موفق به SP-07 می‌رود. پیک هرگز اکانت یا نقش سیستمی ندارد.

| دسته | Deliverable دقیق |
|------|-------------------|
| جداول (migration) | `shipments` (`order_id, seller_id, courier_name, courier_phone, status, tracking_code, delivered_at`) + ستون‌های افزوده `reissue_count` و `last_code_request_at` (تصمیم — برای سقف ۳ صدور و فاصله ۴ ساعته)؛ `delivery_codes` (`shipment_id, **code_hash** (هرگز کد خام), expires_at, attempts, locked_until, issued_to, issued_at`)؛ `delivery_confirmations` (`shipment_id, code_ok, receiver_name, relation, photo, gps, confirmed_at`)؛ `delivery_web_tokens` (`shipment_id, token, expires_at, used_at` — **تک‌مصرف**)؛ `delivery_code_requests` (تصمیم — لاگ ضدسوءاستفاده: چه کسی، کی، چرا، IP و دستگاه) |
| Endpointهای بک‌اند (`/api/v1`) | فروشنده: `POST /seller/orders/{id}/shipment`، `GET /seller/orders/{id}/shipment`، `POST /seller/orders/{id}/delivery-code/request`، `POST /seller/orders/{id}/courier-link` — مشتری: `GET /orders/{id}/shipment`، `POST /orders/{id}/delivery-code/request` — پیک (بدون JWT، توکن): `GET /delivery/{token}`، `POST /delivery/{token}/verify`، `POST /delivery/{token}/reissue-code`، `POST /delivery/{token}/failure` — ادمین: `POST /admin/orders/{id}/manual-delivery`، `GET /admin/delivery-failures` (مسیرهای `/delivery/*` افزوده و تصمیم‌اند) |
| صفحات اپ Flutter | `order-tracking.png` (شمارش: «کد تحویل از {ساعت} فعال می‌شود» ← «کد شما: ۴۵۸۲۱۹»)، `orders.png` (جزئیات سفارش + دکمه «کد تحویل را دریافت نکردم») |
| صفحات وب | پیک: **`courier-delivery.png`** (صفحه عمومی وب — بدون نصب اپ)؛ فروشنده: `seller-shipping.png` (مدیریت ارسال و پیک‌ها، ثبت در مهلت ۲۴ ساعته، «درخواست کد جدید»، «تحویل ناموفق»)؛ ادمین: صفحه ۲۱ «تأیید تحویل دستی» + «گزارش تحویل ناموفق» (آمار رمزهای اشتباه، تحویل‌های معلق، اختلاف‌ها) |
| مهاجرت‌ها | ۲ نسخه‌بندی‌شده + rollback در staging + seed (سفارش + shipment + کد آزمایشی) |
| تست | unit + integration + contract طبق §۴ |
| مستندات | Swagger کامل (نمونه درخواست عمومی `/delivery/{token}` خارج از JWT + قالب‌های `SMS-SHIPPED/DELIVERED/CODE-REISSUE/CODE-LOCK`) |

**خارج از اسکوپ (به SPهای دیگر):**
- بازگشت وجه تحویل ناموفق/لغو → **SP-07** (اینجا فقط رویداد `delivery.failed`/`order.cancelled` صادر می‌شود).
- مرجوعی ۷ روزه (`return_requests`) → **SP-10**؛ موتور اعلان + یادآوری ۳۰ دقیقه قبل از بازه → **SP-11**؛ تیکت → **SP-14** (اینجا فقط insert تیکت خودکار).
- تغییر وضعیت پایه سفارش و صفحه «سفارش‌های فروشنده» → **SP-06**؛ اینجا فقط زیرسیستم ارسال/تحویل.
- امتیاز منفی فروشنده بابت تحویل ناموفق → **SP-12** (رویداد با `order_id` ثبت می‌شود).

## ۳. اقدامات و مراحل (گام‌به‌گام با Milestone)

### M-08.۱ — اسکیمای ارسال و صدور shipment (روز ۱)
1. migration `sp08_delivery` برای `shipments, delivery_codes, delivery_confirmations, delivery_web_tokens, delivery_code_requests` بنویس (نام و ستون‌ها دقیقاً ERD `project-document.md:4802-4805` + ستون‌های افزوده‌شده در §۱).
2. `POST /seller/orders/{id}/shipment` را بساز: فروشنده پیک/روش/کد رهگیری را ثبت می‌کند و سفارش به **«در حال ارسال»** می‌رود؛ **مهلت ثبت اطلاعات ارسال ۲۴ ساعت** از «تحویل پیک» — عدم ثبت = لغو خودکار + بازگشت وجه + اخطار ثبت در پرونده فروشنده.
3. تأیید کن فقط یک shipment فعال per سفارش (سفارش‌های چندفروشگاهی: هر سفارش shipment و کد مستقل خودش را دارد).
**خروجی:** جداول + endpoint ثبت ارسال. **معیار قبولی:** `seller_24h_no_shipping_info_auto_cancel` سبز.

### M-08.۲ — کد ۶ رقمی هش‌شده + اعتبارسنجی (روز ۲-۳)
1. با رسیدن به «در حال ارسال» به‌طور خودکار کد ۶ رقمی تصادفی بساز، **فقط `code_hash` را ذخیره کن** (کد خام نه در دیتابیس نه در لاگ)، `expires_at = now + ۲۴ ساعت`، `attempts = 0`.
2. ارسال همزمان **پوش + پیامک** با قالب `SMS-SHIPPED`: `سفارش {شماره} ارسال شد. کد تحویل شما: {کد_۶رقم} — در اختیار هیچ‌کس جز گیرنده قرار نگیرد.`
3. اعتبارسنجی `POST /delivery/{token}/verify`: هر بار `attempts + 1`؛ نادرست → پیام پیک **«کد اشتباه است. {n} تلاش دیگر دارید»**؛ **۳ تلاش اشتباه → `locked_until = now + ۱۵ دقیقه` + هشدار `SMS-CODE-LOCK`** به مشتری و پیگیری در «گزارش تحویل ناموفق» ادمین؛ منقضی → دکمه درخواست کد جدید.
4. کد صحیح → **فقط با تکمیل همه فیلدها تحویل ثبت می‌شود**: نام گیرنده + نسبت با خریدار (خود خریدار/خانواده/همکار/همسایه/سایر) + **عکس بسته اجباری** + نام پیک + ساعت تحویل (`confirmed_at`) + لوکیشن اختیاری؛ سپس وضعیت «تحویل شده»، اعلان «تحویل با موفقیت ثبت شد» + `SMS-DELIVERED`، ابطال لینک وب و **انتشار رویداد `delivery.confirmed`** (کانسیومر idempotent در SP-07).
**خروجی:** سرویس کد تحویل. **معیار قبولی:** تست‌های `code_*` §۴ سبز و `SELECT` روی `delivery_codes` هیچ کد خامی نشان نمی‌دهد.

### M-08.۳ — درخواست کد جدید با سقف مشترک ۳ (روز ۳-۴)
1. سه مسیر درخواست را با **سقف مشترک ۳ صدور کد در هر سفارش** پیاده کن: فروشنده (الزام انتخاب دلیل از لیست)، مشتری (بدون دلیل، **هر ۴ ساعت یک‌بار**، فقط از صفحه پیگیری)، پیک (فقط وقتی پیام «کد منقضی/اشتباه» دیده). ادمین از «تأیید تحویل دستی» نامحدود با ثبت در `audit_logs`.
2. رفتار تأیید درخواست: ① کد قبلی **فوراً باطل** (حتی منقضی‌نشده) ② کد نو با عمر **۲۴ ساعت** ③ پوش + پیامک `SMS-CODE-REISSUE`: `کد تحویل جدید سفارش {شماره}: {کد_۶رقم} — کد قبلی باطل شد.` ④ لینک جدید برای پیک و ابطال لینک قبلی ⑤ صفر شدن شمارنده تلاش ⑥ رویداد در تایم‌لاین + اعلان داخلی به فروشنده.
3. رفتار اتمام سقف: دکمه فروشنده غیرفعال + **«۳ بار مجاز گذشت — از تحویل دستی استفاده کنید»**؛ مشتری/پیک: **«برای درخواست مجدد با فروشنده/پشتیبانی تماس بگیرید»**؛ **۲۴ ساعت از آخرین درخواست بدون ثبت تحویل → تیکت خودکار** + اعلان ادمین + پیشنهاد «تأیید تحویل دستی»؛ پیک «تحویل ناموفق» ثبت کرده و فروشنده ۲۴ ساعت اقدام نکرده → تیکت خودکار + وضعیت «معلق — نیازمند اقدام فروشنده».
4. ضدسوءاستفاده: هر درخواست فقط با دسترسی به همان سفارش؛ لاگ کامل `delivery_code_requests` (چه کسی، کی، چرا، IP و دستگاه)؛ پس از سقف سفارش بدون تأیید ادمین باز نمی‌شود.
**خروجی:** سرویس reissue. **معیار قبولی:** `reissue_shared_cap_3_issuances` و `auto_ticket_after_24h_undelivered` سبز.

### M-08.۴ — لینک وب پیک (روز ۴-۶)
1. `POST /seller/orders/{id}/courier-link`: تولید توکن تصادفی غیرقابل حدس → URL اختصاصی هر سفارش؛ فروشنده آن را با واتساپ/پیامک/هر روشی برای پیک می‌فرستد.
2. قواعد: **بدون اپ، بدون ثبت‌نام، بدون اکانت و بدون نقش برای پیک** (خواندنی از §۲ و §۱.۶ معماری و قاعده ۸ README)؛ عمر **۲۴ ساعت یا تا پس از تحویل موفق**؛ `used_at` پس از تحویل پر می‌شود (**تک‌مصرف**)؛ خارج از چرخه JWT.
3. صفحه `courier-delivery.png` را بساز: هدر (لوگو + شماره سفارش)، آدرس مشتری + تعداد اقلام + نام فروشگاه، نام و موبایل **گیرنده** (موبایل خریدار نمایش داده نمی‌شود)، فیلد کد ۶ رقمی، نام گیرنده، نسبت، **آپلود عکس (اجباری)**، لوکیشن اختیاری، دکمه ثبت **فقط با کد صحیح**، گزینه‌های «مشتری در دسترس نیست» / «آدرس اشتباه» و دکمه «کد کار نمی‌کند».
4. توکن منقضی/نامعتبر/استفاده‌شده → صفحه خطا با پیام «لینک تحویل منقضی شده است» + راهنمای تماس با فروشنده.
**خروجی:** endpointهای عمومی + صفحه وب. **معیار قبولی:** سناریوی UAT پیوست ب #۹ سبز (لینک پیک پس از ۲۴ ساعت → منقضی).

### M-08.۵ — جریان‌های ناموفق + تأیید دستی ادمین (روز ۶-۷)
1. `POST /delivery/{token}/failure`: «مشتری در دسترس نیست» → تحویل ناموفق + رویداد بازگشت کامل وجه (SP-07) + ثبت برای نرخ فروشنده؛ «آدرس اشتباه» → تیکت + تعیین تکلیف ادمین در **۲۴ ساعت**.
2. `POST /admin/orders/{id}/manual-delivery`: باز کردن کد منقضی، ثبت تحویل با دلیل در `audit_logs`، ابطال لینک، انتشار `delivery.confirmed`.
3. تأیید کن چندفروشگاهی: هر فروشگاه مستقل وضعیت و کد تحویل خودش را دارد؛ تحویل یکی روی بقیه اثر ندارد.
**خروجی:** فلوهای خطا + صفحه ادمین. **معیار قبولی:** هر دو فلو با لاگ `audit_logs` و بدون retry خودکار مالی.

### M-08.۶ — صفحات، تست، Swagger (روز ۷-۸)
1. `order-tracking.png` (شمارنده کد + تایم‌لاین)، دکمه «کد تحویل را دریافت نکردم» در `orders.png`، `seller-shipping.png` و صفحه ادمین ۲۱ را با متن‌های دقیق UI Copy بساز.
2. تست‌های §۴ را سبز کن؛ `flutter test` و `npm test` را اجرا کن.
3. Swagger را از کد تولید و صورت‌جلسه تحویل M3/«MVP قابل دمو» (پایان SP-08) را ثبت کن.
**خروجی:** صفحات + گزارش تست + Swagger. **معیار قبولی:** DoD §۴ صددرصد + دمو کامل «لاگین تا تحویل با کد ۶ رقمی» ضبط‌شده.

## ۴. روش تست و پذیرش (DoD)

**تست خودکار (نام تست‌ها):** `shipment_issued_code_push_sms_on_shipping_status`، `code_stored_hash_only_no_plaintext`، `code_expires_after_24h`، `wrong_code_decrements_attempts_message`، `third_wrong_attempt_locks_15min_and_alerts`، `delivery_requires_code_receiver_relation_photo_courier_time`، `reissue_seller_requires_reason`، `reissue_client_every_4h`، `reissue_courier_only_after_error_seen`، `reissue_shared_cap_3_issuances`، `reissue_revokes_old_code_resets_attempts_new_token`، `web_token_single_use_invalid_after_delivery`، `web_token_expired_24h_rejected`، `no_courier_account_or_role_created`، `auto_ticket_after_24h_undelivered`، `seller_24h_no_shipping_info_auto_cancel`، `multi_store_independent_shipments_and_codes`.

**سناریوی دستی گام‌به‌گام (👤 کارفرما، گوشی اول مشتری + گوشی دوم پیک بدون اپ):**
1. **صدور کد:** فروشنده در `seller-shipping.png` سفارش را «در حال ارسال» می‌کند → بلافاصله پوش + `SMS-SHIPPED` با کد ۶ رقمی؛ در `order-tracking.png` نوشته شود **«کد تحویل از {ساعت} فعال می‌شود»** و سپس **«کد شما: ۴۵۸۲۱۹»** (عدد نمونه).
2. **UAT پیوست ب #۵ (کد اشتباه):** پیک در صفحه وب کد اشتباه وارد کند → رد + پیام **«کد اشتباه است. ۲ تلاش دیگر دارید»**؛ بار دوم هم اشتباه → **«کد اشتباه است. ۱ تلاش دیگر دارید»**؛ بار سوم → قفل **۱۵ دقیقه** + `SMS-CODE-LOCK` به مشتری + ردیف در «گزارش تحویل ناموفق» ادمین.
3. **تحویل موفق:** کد صحیح + نام گیرنده + نسبت + عکس بسته → بدون عکس دکمه ثبت غیرفعال و خطای «این فیلد الزامی است»؛ با عکس: **«تحویل با موفقیت ثبت شد»** + `SMS-DELIVERED` + ابطال لینک + آزادسازی اسکرو در کیف پول فروشنده (SP-07).
4. **درخواست کد جدید:** مشتری دکمه «کد تحویل را دریافت نکردم» را دوباره در کمتر از ۴ ساعت بزند → خطا؛ پس از ۴ ساعت → کد جدید، کد قبلی باطل، Toast **«کد جدید ارسال شد»** و `SMS-CODE-REISSUE`.
5. **سقف ۳ صدور:** درخواست از فروشنده/مشتری/پیک تا سقف ۳ → بار چهارم دکمه غیرفعال + **«۳ بار مجاز گذشت — از تحویل دستی استفاده کنید»**؛ سپس ۲۴ ساعت بدون تحویل (کلون با `last_code_request_at` قدیمی) → **تیکت خودکار** + اعلان ادمین.
6. **UAT پیوست ب #۹ (لینک منقضی):** لینکی را با `expires_at` قدیمی باز کنید → صفحه **«لینک تحویل منقضی شده است»**؛ پس از تحویل موفق همان لینک را دوباره باز کنید → غیرفعال (تک‌مصرف).
7. **تأیید تحویل دستی:** ادمین در صفحه ۲۱ با دلیل ثبت‌شده در `audit_logs` تحویل را تأیید می‌کند و لینک باطل می‌شود.

**جدول خطاهای پرتکرار:**

| code | HTTP | پیام فارسی دقیق | سناریو |
|------|------|----------------|--------|
| `DELIVERY_CODE_INVALID` *(افزوده — تصمیم، چون API سند کد ندارد)* | 422 | «کد اشتباه است. {n} تلاش دیگر دارید» | ورود کد نادرست |
| `DELIVERY_CODE_LOCKED` *(افزوده)* | 429 | «۳ بار کد تحویل اشتباه وارد شد. به مدت ۱۵ دقیقه قفل است.» | بعد از ۳ تلاش |
| `DELIVERY_TOKEN_EXPIRED` *(افزوده)* | 404 | «لینک تحویل منقضی شده است» | توکن >۲۴ ساعت یا استفاده‌شده |
| `ORDER_STATE_CONFLICT` | 409 | «سفارش تازه‌تر شده است. بروزرسانی کنید» | درخواست کد/ثبت ارسال روی وضعیت ناسازگار |
| `VALIDATION_ERROR` | 400 | «این فیلد الزامی است» / «حجم تصویر حداکثر ۵ مگابایت است» | بدون عکس بسته یا فرمت غیرJPG/PNG |
| `NOT_FOUND` | 404 | «سفارش یافت نشد» | توکن/شناسه نامعتبر |
| `RATE_LIMIT_EXCEEDED` | 429 | هدر `Retry-After` | بیش از ۶۰ درخواست/دقیقه مسیرهای عمومی |
